Rule 1

You can't tell where a program is going to spend its time. Bottlenecks occur in surprising places, so don't try to second guess and put in a speed hack until you've proven that's where the bottleneck is.

Rule 2

Measure. Don't tune for speed until you've measured, and even then don't unless one part of the code overwhelms the rest.

Infino & Infino Cloud

Infino

  • Embedded, open source retrieval library built in Rust
  • Supports millisecond SQL, FTS, vector & hybrid queries over TBs of data, and amongst the fastest in each (benchmarks)
  • Data stays plain Parquet, on local disk or object storage
  • Use it from Python, Node.js or Rust

Infino Cloud

  • Managed offering of Infino (platform.infino.ws)
  • Same API: change only the connect target
  • Zero config setup: optimize and gc run for you
  • Enterprise features
~1.5 min. Be ready to back up "amongst the fastest" (infino.ai/benchmarks): on ClickBench (benchmark.clickhouse.com, infino folder upstream) Infino is #1 among search engines. VectorDBBench (zilliztech/VectorDBBench#863) and Search Benchmark, the Game (quickwit-oss/search-benchmark-game#92) PRs are still open, so do not claim a spot on those boards yet. Why latency is hard for us: sub-second queries over terabytes, but one query fans out into many object storage reads; every read is a network round trip, so one serial loop adds seconds; logs say THAT a query was slow, not WHERE; local profilers don't see time spent waiting on the network. The point: with this many network reads, the only way to see where time goes is tracing.

OpenTelemetry

An open standard for producing and shipping telemetry: traces, metrics and logs.

What it is

  • An API and SDK for every major language
  • OTLP: one wire format for all three signals
  • Vendor neutral, a CNCF project

Why we need it

  • Instrument once, change backends freely
  • One pipeline instead of one agent per signal
  • Shared trace id and service.name: Grafana jumps from a log to its trace
~1 min. OTel is the standard; LGTM is just one place to send it. Our code never names Loki, Tempo or Mimir: it speaks OTLP, and config decides where each signal goes.

~1.5 min. The span and the event are real infino code (the span attribute is trimmed from a cfg_attr: in infino these detailed spans sit behind the detailed-tracing feature). Spans have a start and an end, so they become traces. Events are point-in-time, so they become logs. The metric lines are an example: the infino library emits no metrics itself. Metrics: tracing-opentelemetry's MetricsLayer (the "metrics" cargo feature) turns any event field prefixed monotonic_counter., counter. or histogram. into an OTel metric; the other fields become attributes. Honest caveats if asked: (1) Infino Cloud today calls the OTel meter API directly instead, same SDK and exporter, only the call site differs. (2) A metric event is still an event, so the log bridge ships it to Loki too unless you filter it. (3) Gauges need the metrics_gauge_unstable feature.

The three layers sit on one tracing_subscriber::registry(), which also prints to stdout.

~1.5 min. Read it as nested boxes: the engine only emits spans and events; the process that embeds it (gateway or worker) owns the subscriber, the SDK and the exporters; the node runs the process plus Alloy. Each process sends OTLP/HTTP (binary protobuf) to the Alloy on its node, and Alloy routes each signal: traces to Tempo, metrics to Mimir, logs to Loki. Alloy also reads the systemd journal, to catch what tracing cannot see: a panic before logging starts, an OOM kill, a unit dying. Traces and logs are batched; metrics are aggregated in memory and pushed by a PeriodicReader. If asked: an event inside a span also becomes a span event, and an ERROR event marks the span as failed. Logs carry the trace id, so Loki links to Tempo. Sampling is the SDK default (parent-based, always on), so a trace exports whole or not at all.
